# Agent 构建失败复盘与执行器修复

本文对应 2026-10-09 日历项目增加注册登录时的失败。修复对象是平台 Agent、工具和验收执行器，不是手工重写该项目的业务代码。

## 1. 实际发生了什么

项目：`014d2cbf484a4129bdc46ecfc8b22d17`。失败任务：`8927b035-9e8c-461d-8945-e6824f51c992`，需求是“增加注册登录功能”。数据库记录为北京时间 19:27:01 开始、19:56:45 失败，共 **29 分 44 秒**。

## 2. 根因与修复

### 2.1 模型调用包装器破坏接口

`ModelGateway.chat` 支持 `tools, max_tokens, reasoning`；旧预算包装器只接受第四个位置参数 `tools`。跨阶段恢复 pending 请求时，内部调用传入第五个位置参数，因此在运行很久、切换诊断阶段时才暴露 TypeError。

修复：提取 `agent_delivery.budgeted_chat`，完整保留位置/关键字参数语义；内部恢复调用使用命名参数。恢复旧请求先核对原载荷和计费 ID，不执行旧响应中的工具提案；新增恢复提示不能阻止原请求结算。新请求的输出上限按实际输入估计动态裁剪。

### 2.2 平台制造了假的目录冲突

计划写 `frontend.directory = src`，现有代码在 `src/App.tsx`，旧检查却寻找 `src/src/`。Agent 被要求修复一个并不存在的业务问题。旧检查还把小应用集中在 App 中当作交付失败，诱导不必要的拆文件操作。

修复：同时识别应用根目录和源码目录，覆盖 `. / src / ./src / frontend / frontend/src / web` 等布局；真实偏差返回候选入口和配置检查说明；模块数量不再作为功能验收门槛。已安装模板仍保留必要依赖与入口检查。

### 2.3 无进展恢复没有收敛

读取、解释和重复诊断不等于实现进展。旧恢复循环主要受很大的总预算控制，易继续消耗调用；滑动证据列表、成功输出中的耗时及随机值还会改变诊断缓存键。

修复：相同源码、任务状态和需求成功证据连续 18 轮不变时，保存检查点并退出无进展循环；新人工任务重置该计数，同一任务自动恢复继续使用原计数。诊断缓存使用当前版本的成功检查身份、具体失败签名和真实需求缺口，忽略新证据编号、耗时等无关变化。没有当前失败或验收缺口时使用执行器直接反馈，避免独立模型再猜业务问题。

该保护不能保证任意任务在 18 轮内完成：有真实源码变化或新需求证据时继续执行。源码来回修改仍需后续通过变化语义和重复版本检测进一步约束。

### 2.4 上下文策略同时存在两个极端

大窗口模型默认携带大量历史上下文，输入成本与延迟逐轮累积；128K 模型又被固定减去 132K 预留，目标落到 4K，工具定义本身就可能触发反复摘要。

修复：Compose 默认 `AGENT_CONTEXT_TOKENS=auto`，执行工作集按 simple / medium / complex 使用 32K / 48K / 96K 目标；数字配置仍优先。根据模型窗口计算预留，取消固定减去 132K。完整工具结果、源码版本和审计保留在会话存储中，可按需读回。

恢复、任务缺口、工程偏差、完成缺口反馈按主题保留最新一份，旧全文存入审计事件。保留真实用户要求和 assistant/tool 配对。压缩会改变提供商缓存前缀，因此不是越频繁越好；现有工作集和压缩增长阈值继续防止重复摘要。

### 2.5 验收策略与能力选择互相冲突

旧普通档一方面限制 API 最多检查一次，另一方面要求真实功能成功链路；注册→登录→业务数据回读本来就需要多次请求。普通档完成检查又跳过全部 API 要求，导致构建或错误路径可能被误解为足够证据。浏览器工具未开启也容易被模型错误解释成整个功能必须延期。

修复：显式 API 要求统一参与工具开放、失败处理、需求完成检查、系统接口合同和最终回读判断；不再受一次检查限制，不因“普通档”跳过真实成功证据。可选扩展需求继续允许演示路径。不开启浏览器工具时遵循实际合同和可用命令/API 验证，另行明确交互检查范围，不能因此伪称完整 DOM 流程通过。

`PREVIEW_READY` 仍明确是演示检查点，不是 `COMPLETE`。源码改变后需要新证据；构建、健康检查、预期 401 和旧版本证据都不能替代明确接口合同的成功结果。

### 2.6 工具掩盖真实失败、制造假的 404

旧 shell 仅有 pipefail；Python 断言失败后接一条成功命令，整个 shell 仍可能返回 0。

修复：`run_shell` 启用 `errexit + pipefail`。预期失败使用 `if` / `||` 明确表达，保留真实非零退出码。shell 的显式错误忽略仍遵循 Bash 语义，不能把它当成任意脚本都不会伪造成功的保证。

预览运行器以前只通过启动命令是否含 `$BASE_PATH` 判断路径感知，漏掉 `vite.config.ts` 读取环境变量的场景；健康检查通过后 API 仍被错误剥离前缀。HTTP 工具还会对 runtime_check 返回的完整当前运行路径重复加前缀。

修复：运行器识别 Vite 配置中的 BASE_PATH，支持 `base_aware` 显式覆盖；HTTP 与浏览器工具统一处理当前 runtime 前缀，避免同一地址被重复拼接。非标准配置仍可显式声明，无需 Agent 为平台路径问题修改业务路由。

## 3. 与 Claude Code / OpenCode 的差距怎么看

Claude Code 的公开工作方式强调上下文收集、行动、验证的反馈循环，并会先清理旧工具输出，再按需压缩上下文。[官方说明](https://code.claude.com/docs/en/how-claude-code-works)

OpenCode 区分可执行代码修改的 Build agent 与受工具限制的 Plan agent。[官方说明](https://opencode.ai/docs/agents/)

本项目的问题不是缺少循环或工具数量，而是执行器把错误合同当成业务失败、已成功证据无法促成收敛、上下文与验收策略互相矛盾。增加规划层、反复让另一个模型诊断、扩大 Token/轮数，都不能替代修复这些确定性错误。

模型本身的规划和代码能力也会影响结果，但这里没有同模型、同仓库、同需求的对照实验，不能据此宣称已追平其他 Agent，或承诺修复后的所有任务都几分钟完成。

## 4. 验证与后续优先级

回归覆盖预算包装器位置参数、跨阶段 pending 恢复、原请求身份保持、动态输出预留、src 布局、shell 断言失败、诊断缓存、无进展退出、反馈去重、普通档多步骤 API 验收、预览前缀和接口合同证据。最终完整范围运行 **152 个测试，150 通过、2 个条件跳过**；随后上下文目标变更时清理旧压缩下限的调整，又通过 11 项定向回归。验证日志保存在 `.deploy/agent-incident-complete-tests.log` 和 `.deploy/agent-incident-last-change-tests.log`。

可选的真实 CLI 全栈烟测因 npm 安装在 120 秒内未完成而失败，不能计作功能通过。新增 `RUN_TEMPLATE_SMOKE=1` 的预装模板烟测入口，使用临时应用检查真实浏览器写入、刷新、服务重启后的数据回读及最终交付检查，**已通过，耗时约 31 秒**，日志为 `.deploy/agent-runtime-template-smoke.log`。该结果验证平台工具与运行链路，不等于模型自主完成原日历需求的耗时基准。

2026-10-09 已将修复镜像部署到 `agent-service`、`backend` 和 `preview`，三者健康检查通过，Agent 服务确认使用 `AGENT_CONTEXT_TOKENS=auto`。既有项目 Worker 在下一次新构建入队、且没有运行中任务时采用新镜像；不会自动重跑历史失败任务。

后续优先级：

1. **P0：验收与工具正确性。** 固定上述案例作为回归；明确需求、场景、工具实际能力使用同一合同。每次真实失败应能定位到请求、命令或运行版本。
2. **P1：按任务评估效率。** 建立简单增量修改、认证 CRUD、现有全栈项目三类固定样本，记录完成率、调用数、输入 Token、首个可运行版本和最终验收耗时。使用相同起始快照和模型才能比较优化效果。
3. **P1：更准确的无进展识别。** 识别源码版本往返、仅元数据变化、相同失败签名，并区分有效判别实验与重复探测。
4. **P2：复用稳定的工程能力。** 沉淀平台数据库、认证和预览路径的可运行契约，缩小生成环境配置的自由度；按相关文件版本维护上下文工作集，测量真实服务商缓存收益。

本次没有重写日历业务，也没有把未执行的浏览器交互记为成功；已存在的失败任务与账单保留原始记录。
