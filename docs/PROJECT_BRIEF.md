# Atoms Demo 项目简要说明

[返回 README](../README.md)

本文依据 2026-10-09 当前工作区的代码与实现记录整理。项目是一个 Atoms 风格的 AI 项目构建平台，核心流程为：提交自然语言需求 → Agent 规划与编码 → 构建和运行检查 → 预览、修改与版本管理 → 发布应用或下载文件成果。

## 实现思路与关键取舍

前端使用 React、TypeScript 和 Monaco，承载项目管理、对话、代码编辑及成果预览；后端使用 Python / FastAPI，管理认证、任务、文件、计费和发布。PostgreSQL 保存平台业务记录并为生成应用分配独立数据库 Schema，MinIO 保存发布资源与镜像归档，Docker 承载项目执行和发布环境。

Agent 采用“模型决策 + 受约束工具执行”的方式：先形成需求、任务和接口约定，再调用源码搜索、文件读写、命令、构建及运行验收工具。计划、会话和验证证据持续保存，支持停止后继续和新增需求的增量开发。

| 关键取舍 | 实现方式与原因 |
| --- | --- |
| 先交付可运行演示 | 普通档优先完成页面和核心交互；缺少外部凭据时提供明确标注的模拟适配或记录延期项。降低等待配置的成本，同时保留“演示可用”和“完整验收”的区别。 |
| 标准模板与技术栈选择 | 未指定技术栈时使用预置 React / TypeScript 模板，必要时组合 FastAPI 后端并复用预热依赖；明确指定技术栈和已有项目优先遵循原要求，减少初始化成本。 |
| 验收强度分档 | 普通、深度、高级采用不同规划范围与验收策略。所有 Web 交付检查真实构建和页面启动，更深档位覆盖核心业务及边界；浏览器交互工具可选，避免简单需求承担过多执行成本。 |
| 项目隔离与部署复杂度 | 项目使用独立容器、UID、数据库角色和资源限额，但共享宿主机与托管 PostgreSQL。当前便于单机部署和维护，多机调度及更强运行边界仍需继续建设。 |
| 开发与发布分离 | 发布冻结源码、依赖和前端产物，使用独立运行容器及生产数据库 Schema；候选版本就绪后切换，失败保留旧版本。提升线上稳定性，也增加镜像归档、数据迁移和资源管理成本。 |

## 当前完成程度

**核心产品流程已有实现，可以围绕真实项目进行构建、预览、修改和发布；商业化、协作及规模化运维仍有缺口。** 平台功能是否实现、某个生成项目是否完整，以及部署环境是否配置到位，需要分别判断。

| 模块 | 已完成的主要内容 |
| --- | --- |
| 账户与项目 | 邮箱注册登录、资料与偏好、项目创建、收藏、重命名、隐私、克隆和删除。 |
| AI 构建 | 多模型选择、三档构建、专家技能、任务规划、增量修改、源码工具、真实构建、运行检查及演示交付。 |
| 持续执行 | 会话持久化、上下文整理、停止与继续、请求恢复、任务状态推送及轮询补读。 |
| 工作区与预览 | 代码编辑、文件搜索、上传下载、命令执行、前后端预览、日志诊断及页面元素 / 文本修改。 |
| 版本与成果 | 源码和二进制快照、异步版本还原及失败回滚；文档、演示文稿、表格等成果的生成、预览与下载。 |
| 发布与连接器 | 独立应用版本发布、历史发布版本恢复、公开访问及域名验证；GitHub 授权导入 / 同步、项目数据库连接器。 |
| 用量与部署 | 模型额度预留和结算、积分账本、邀请奖励、模拟订单支付；Docker Compose 一键启动、健康检查和项目资源限制。 |

尚未完成或仍有限制的部分：

- **真实商业支付**：套餐和充值使用本地模拟支付，未接通真实收款、支付回调及财务发票流程。
- **团队协作**：已支持工作区资料，尚无完整的成员邀请、团队角色权限和多人实时协同编辑。
- **自动域名运维**：已有 DNS 所有权检查和路由，公网入口与 TLS 证书仍需部署配置。
- **移动与浏览器兼容范围**：App 类型不等于原生应用打包或商店上架；发布沙盒对 Cookie 登录、IndexedDB、Service Worker 仍有限制。
- **数据恢复范围**：源码版本还原不恢复业务数据库；发布版本回退保留生产数据，不自动撤销数据库迁移。
- **外部服务与产品细节**：模型、GitHub、语音等依赖配置与授权；语言和通知偏好已保存，但完整双语界面、邮件通知及通知中心尚未形成完整闭环。
- **规模化与验证**：当前部署以单机 Docker 为主，未形成多机调度与高可用体系。仓库有专项回归和部署验证记录，但未建立覆盖所有模型、需求和环境的统一成功率基准；本次文档整理未重新执行全套功能验收。

## 后续扩展与优先级

优先保障构建结果可靠、线上版本稳定，再增加商业化和协作功能。以下是建议投入方向，不代表已完成或已有排期。

| 优先级 | 建议工作 | 优先级判断及验收目标 |
| --- | --- | --- |
| P0 | 构建与恢复的持续回归 | 固定一组前端、全栈、增量修改和文件成果任务，持续验证停止 / 继续、预览、还原、发布及失败恢复。记录成功率、耗时、Token 成本和失败原因，先解决阻断核心流程的问题。 |
| P1 | 发布与数据运维完善 | 在已有独立发布基础上补齐兼容数据库迁移、备份恢复演练、发布告警和归档清理；将域名与证书配置自动化。验收重点是升级失败保留旧版本、回退后数据可用，以及备份可恢复。 |
| P1 | Agent 成本与维护性优化 | 根据 P0 数据减少重复规划、读取和无效修复循环，逐步拆分较集中的编排逻辑。以相同任务的质量、耗时和成本对比判断收益，避免仅扩大预算。 |
| P2 | 真实支付与协作 | 有商业运营或团队使用需求时，接入真实支付回调、订单对账和成员权限。分别验证幂等到账、异常补偿及跨成员权限边界。 |
| P3 | 规模化与生态扩展 | 在并发需求增长后建设多机任务调度、容量管理和高可用；再扩展专家、模板、连接器及移动应用交付。用实际资源瓶颈和使用反馈决定投入顺序。 |

若只能继续投入一轮时间，建议先完成 P0 的代表性任务回归与失败归因，再针对最常见的问题优化执行链路；这能为后续功能扩展提供可比较的质量依据。
