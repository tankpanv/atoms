# Published application delivery

Public entry points, aliases and SPA deep links return a platform-authored shell. Application HTML runs in an iframe with CSP `sandbox allow-scripts allow-forms allow-modals`; it never gains access to platform cookies or storage. MinIO index files, legacy published directories and legacy HTML all use this entry path. The storage compatibility script runs before application scripts.

The shell seeds frame storage from browser-native storage under a project namespace. Frame writes are accepted only from its own `contentWindow`, with the shell's random bridge token and matching project scope. Local data persists across tabs; sessions are scoped to a tab. Another browser or project does not inherit tokens. Application code cannot choose a platform storage key. Existing preview storage behavior is unchanged. The explicit frame query marker survives SPA history changes and same-frame links: insecure LAN origins do not reliably send `Sec-Fetch-Dest`.

`/api/public/{project_id}/api/...` requires a published, public project for every method. It forwards exclusively to the active immutable release container, never the development runtime. Request cookies and control-plane headers are removed; explicit application Bearer credentials are preserved. Path traversal cannot escape into coordinator operations. OPTIONS does not start a container. Public CORS accepts opaque origins without credentials; the platform CORS allowlist remains restricted.

Frontend assets and complete Docker images are archived in MinIO. Backend code and installed dependencies live in an immutable image, with an independent production database connector and persistent data directory. Activation changes frontend references and backend selection transactionally after readiness checks. Custom server routes and WebSockets are supported; opaque frames retain the Web Storage compatibility layer. Cookie authentication, IndexedDB and service workers retain existing opaque-origin limitations. See [independent publication](INDEPENDENT_PUBLICATION.md) for lifecycle, configuration, rollback and validation.

Regression tests: `backend/tests/test_public_delivery.py` exercises browser storage and session persistence, separate tabs/visitors/projects, deep reloads, platform CORS isolation, API cold starts/reuse, privacy gates and traversal rejection. The actual published HealthLedger app was exercised through the LAN frontend proxy, including registration/login, record creation/readback, reports, trends, refresh and logout.
