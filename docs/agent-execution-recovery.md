# Agent execution contracts and recovery

## Incident evidence

Project `3732500605174871b87013fd87caaa02` had a conditional frontend directory instead of a path, so strict template selection silently missed the default starter. Its plan contained Chinese prose in shell fields. The harness repeatedly ran that prose and got exit 127 although the model explicitly diagnosed this and ran `npm test` successfully. Model-written nested `commands.test` was ignored by flat-only workspace readers. Repeated successful build receipts hid the lack of actual progress. These are platform defects, not proof that the user application is broken.

## Source review

Source snapshots were read from the upstream repositories, not inferred from CLI behavior:

- [OpenCode session processor](https://github.com/anomalyco/opencode/blob/907b3bc518fa48e90e8ec24dd327d13eee71c36c/packages/opencode/src/session/processor.ts): records pending/running/completed/error tool results, captures snapshots/diffs, and detects three identical recent tool inputs before invoking `doom_loop` permissions. That detector is scoped to the assistant message; it does not cover our independent acceptance loop. Our guard spans model turns and harness actions and uses actual source/config fingerprints.
- [OpenCode retry](https://github.com/anomalyco/opencode/blob/907b3bc518fa48e90e8ec24dd327d13eee71c36c/packages/opencode/src/session/retry.ts): classifies transient API errors, uses Retry-After/backoff, caps retries, and excludes context overflow from blind retry. Business/configuration failures require diagnosis, not provider retry.
- [OpenCode Bash implementation](https://github.com/anomalyco/opencode/blob/907b3bc518fa48e90e8ec24dd327d13eee71c36c/packages/core/src/tool/bash.ts): noninteractive subprocess input, bounded capture, timeout and structured exit/output. Preserve output when a timeout occurs so the model can distinguish waiting from failure.
- [Claude Code public command validator](https://github.com/anthropics/claude-code/blob/2bfb629dfaff0c8318047a4beb93cf1dc5b58b18/examples/hooks/bash_command_validator_example.py): validates before tool execution and returns actionable errors to the model rather than executing known bad inputs.
- [Claude Code AGENTS.md insertion source](https://github.com/anthropics/claude-code/blob/2bfb629dfaff0c8318047a4beb93cf1dc5b58b18/mods/agents-md/hooks/files/insertion-index.ts): explicitly orders applicable project instruction files relative to nested directories and memory. In our harness, real template source and guides accompany implementation instead of assuming the model knows the scaffold.

The Claude Code public repository contains examples/plugins/mods; it does not expose the complete proprietary agent runtime. No claim is made that its hidden implementation was inspected or copied.

## Applied behavior

1. Empty projects are identified from actual sources, not an ambiguous planner description. Unspecified-stack new web plans resolve to the versioned platform frontend/fullstack template and canonical commands; requested stacks and existing applications keep their architecture.
2. Plan commands must be real shell strings; paths must be concrete relative paths. Prose is returned to planning as a contract error before implementation starts.
3. Flat and legacy nested workspace command shapes are read consistently by build, test and runtime. Current workspace test configuration overrides stale plan text.
4. Persistent action fingerprints cover both model-issued commands and automatic checks. Unchanged successful build/test checks reuse actual results. Arbitrary successful shell operations are not replayed or memoized as pure checks. Identical failed actions execute at most twice for unchanged source/arguments, then return the original diagnostic without re-execution. Source changes permit new verification; timeout/requirement labels do not disguise duplicate calls.
5. Progress measures source and task status, not receipt IDs or explanatory notes. Three, six and ten stagnant turns trigger an execution checkpoint, with later checkpoints every six stagnant turns. For real failures or six turns of repeated reads/queries without progress, a separate compact planning call receives the actual runner, task/requirement facts and recent receipts and proposes a concrete next implementation/verification; it cannot edit requirements or execute tools. Diagnosis is capped at two calls per failure/progress fingerprint. New valid requirement coverage counts as progress, duplicate receipts do not.
6. Lightweight conformance checks identify wrong source directories, missing planned modules, entry-only applications and removed template dependencies. They are not an exhaustive source audit. Actual runtime/core workflow verification is still required before declaring completion.
7. Timeouts retain captured output and terminate subprocess groups. Budget limits and stop requests still apply; recovery does not create an unbounded allowance.
8. A stage change first reconciles any prior in-flight checkpoint using its exact request identity/payload. A settled response is archived and its unexecuted tool proposals are not replayed into the new workflow. An unresolved response still blocks a new generation, avoiding duplicate provider billing. This fixes the old settled STABILIZE checkpoint that otherwise indefinitely blocked fresh PLAN recovery.
9. Compaction uses hysteresis: when fixed instructions, tool schemas and recent complete groups cannot reach the preferred window, another paid summary requires 8,000 estimated tokens of new growth. The model context ceiling still applies and a real overflow forces compaction. This avoids repeatedly summarizing an unchanged, irreducible context.
10. Recovery uses failures from the current source fingerprint only. Old syntax/dependency failures remain archived for audit but cannot masquerade as active blockers after a changed source has passed its checks.
11. Independent diagnosis receives bounded live service output, including actual API tracebacks; a running process alone is not business verification. A newly observed runtime error permits a fresh bounded diagnosis, followed by restarting affected services and testing the real operation.
12. Browser acceptance preserves the project's browser cookies/storage and sessionStorage across tool calls, isolated from other projects and excluded from source downloads. The preview sandbox preserves sessionStorage on reload within the same browsing context, scoped to its preview route. Logout clears it. Acceptance cache identities include current browser state, so a previous authenticated result cannot mask a later logged-out session. No platform authentication token is injected into application pages.
13. Both successful and failed browser actions report actual visible controls, links and usable selectors. HTML attributes are reported as present rather than invented from implicit browser behavior (for example, an implicit submit button does not necessarily match `button[type=submit]`). Runtime tool instructions explicitly describe automatic service restart after source/config changes.
14. Runtime/static/published preview CSP permits native modal dialogs while retaining opaque-origin sandboxing. Browser click/press accepts an explicit `dialog: "accept"` or `"dismiss"` policy (default dismiss) and records the real dialog. Confirmation flows can be verified without silently deleting data. Invalid reserved-email and assumed-button examples were removed from model tool instructions.
15. Valid model-issued browser setup is separated from formal acceptance. If an incomplete flow incorrectly declares requirement coverage, it runs with coverage removed and a precise adjustment message; it cannot mark a requirement/task done. Invalid action parameters still fail before execution, and final delivery scenes still require complete business assertions. This avoids rejecting login preparation before it can establish the session needed by later checks.
16. The recovery tracker also receives real browser/API/runtime outcomes, not only shell failures. Structured error/status/visible-control facts are retained before clipping long reports. A selector mismatch explicitly directs the executor to correct the observed test target before rewriting a working user interface; real business/server failures still require code repair and retesting.
17. Reported control selectors use actual unique IDs/test IDs or DOM paths with sibling indices. Select controls expose exact option values. Multiline option text is not a selector, and equal button labels must not produce an ambiguous selector. A Chromium regression executes all reported selectors against multiline selects and duplicate buttons.
18. Task context retains successful current-source requirement receipts even after more than twelve failed/setup calls. It also identifies stale source receipts and lists concrete completion issues, so the executor can update task progress using verified results instead of repeatedly checking the same behavior. This changes context selection, not acceptance validity; historical/changed-source proofs cannot silently satisfy final delivery.

## Real regression and limits

The separate deep-mode project `d7d79c8b9fdd44eeb3c3b00f6ea34d1f` installed the actual default frontend/fullstack template and a project PostgreSQL schema. Playwright MCP exercised real login, creation, report, editing, reload persistence, trend values/date filtering, native confirmation and deletion, cross-user 404, and anonymous 401 after logout. The actual platform App Viewer loads its application, not a simulated HTML success page. Test-owned historical filter data was deleted through the application confirmation flow.

The regression reached `PREVIEW_READY` through its bounded checkpoint path; its complete task ledger is still pending. This is evidence of working delivery and the repaired operations, not evidence that every original planned verification completed or that cost/performance is fully solved. No task status or acceptance receipt was fabricated. The original user-stopped project was not resumed after that stop request, and its original monolithic source has not been claimed to be refactored. New runs receive the corrected template policy; existing projects retain their sources.
