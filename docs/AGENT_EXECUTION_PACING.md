# 完整需求优先，演示交付只作为兜底

正常执行始终以全部明确需求实现并通过真实验收为目标。建议轮数仅用于提前调整执行节奏，不用于缩减需求或提前触发演示交付。

此前的实际问题：简单任务的建议 16 轮被直接用于 DeliveryBudget 硬限额，而规划、上下文整理、验收和复核的模型调用也计入同一预算。因此即使配置为 120 次，也可能在约 12 次调用时进入演示交付，规划阶段本身就可能提前消耗这些调用。

现在复杂度仍提供 16/40/120 的建议节奏，但正常预算使用配置上限。演示兜底仍只由实际 token、模型调用/执行轮次或时间接近配置上限触发。兜底阶段独立 token 与次数上限仍为配置的一半；调用和真实用量仍全部计费。

规划和执行调整：

- 先确定共享接口、数据模型和关键技术风险，按完整用户流程拆分可验收功能单元，尽早跑通第一条端到端流程，再完成全部明确要求。
- 约每个建议周期的三分之一检查一次节奏，逐步推进集中实现、需求覆盖、证据关联和最终完整验收。超出建议周期时调整实现方法，不改变目标。
- 连续三轮没有成功写入、新增成功验证或任务完成记录时，提示根据已有源码/错误反馈定位具体阻塞，减少重新扫描、重复设计和重复总结。
- 节奏指令附加在已有实现调用中，不新增“规划模型/总结模型”调用。只保留当前协调指令，避免不断叠加重复提示；已提供的源码观察与会话恢复机制继续复用。
- 已有正确实现可以通过真实验证、任务证据及复核完成，不再强迫改动文件。新项目仍不能把空工作区或仅平台文档当成产品交付，完整需求验收门槛保留。
- 会话监控分别记录配置上限、建议轮数和连续无进展轮数。

验证：集成回归确认“规划已经使用 20 次调用、配置 120 次”的简单任务仍进入 COMPLETE，而不是因建议 16 轮进入 STABILIZE/PREVIEW_READY；确认已有正确 CLI 可在不改源码的情况下完成实际命令验证和完整验收；预算接近耗尽时的兜底和独立停止条件继续通过测试。
